# Build-identity stamping in notarized builds

**Written 2026-05-18** in response to the architect's observation
that the 16:55 Comprador `.diag` reported `Version: 0.1.0 (1)` —
neither the real release version nor the git hash.

## What's wrong

`MenuBarApp/Info.plist` hardcodes:
```xml
<key>CFBundleVersion</key>
<string>1</string>
<key>CFBundleShortVersionString</key>
<string>0.1.0</string>
```

These have never been updated. Every release since v0.1.0 reports
itself to macOS as `0.1.0 (1)`. This affects:

- macOS resource-pressure `.diag` files (the trail of how we figured
  out today's regression)
- `xcrun notarytool log` output
- About box (if we had one)
- Spotlight metadata for the .app
- The "Get Info" pane in Finder
- Any future Sparkle auto-update version-comparison
- Crash report attribution

The clickable Build menu item in `app-swiftc` (powered by
`BuildInfo.id` generated by the Makefile) is the only place the
real build identity surfaces. Everywhere else, the system sees the
lie.

## Goal

For every notarized distribution build:
- `CFBundleShortVersionString` = the release version (e.g., `0.3.4`)
- `CFBundleVersion` = the git hash + dirty marker (e.g., `20ea0705`
  or `20ea0705-dirty`)

For development builds (`make app-swiftc`):
- Same treatment so .diag dumps during development are accurate
- The "dirty" suffix on `CFBundleVersion` flags uncommitted state

## Mechanism

The Makefile already computes `BUILD_ID := $(git rev-parse --short
HEAD)$(-dirty if working tree dirty)`. Reuse it.

Add a `RELEASE_VERSION` variable, sourced from `git describe --tags`
or hardcoded per-release. Probably hardcoded — there's a release-
cutting step that updates `Makefile`'s `RELEASE_VERSION` and the
CHANGELOG together.

At app-bundle assembly time (in `app-swiftc` or wherever the
`Info.plist` gets copied into the bundle), use `PlistBuddy`:

```makefile
RELEASE_VERSION := 0.3.4
BUILD_ID := $(shell git rev-parse --short HEAD 2>/dev/null)$(shell git diff --quiet 2>/dev/null || echo "-dirty")

# (existing app-swiftc steps)
cp MenuBarApp/Info.plist $(BUNDLE)/Contents/Info.plist
/usr/libexec/PlistBuddy \
    -c "Set :CFBundleShortVersionString $(RELEASE_VERSION)" \
    -c "Set :CFBundleVersion $(BUILD_ID)" \
    $(BUNDLE)/Contents/Info.plist
```

Done. Apple's notarization checks don't reject non-numeric
`CFBundleVersion` for Developer ID distribution. App-Store
submissions have stricter rules, but Comprador is not App-Store-
distributed (per CLAUDE.md "Non-Goals").

## Verification

After build, check:

```bash
defaults read /path/to/Comprador.app/Contents/Info.plist CFBundleShortVersionString
defaults read /path/to/Comprador.app/Contents/Info.plist CFBundleVersion
```

Expected output:
```
0.3.4
20ea0705
```

Then trigger a resource alert (e.g., a long-running bridge during
prefetch) and check the resulting `.diag` reports the same version
+ build.

## Caveats

1. **PlistBuddy mutates the Info.plist after `cp`.** The codesign
   step happens after this; the signature covers the updated plist.
   Order matters in the Makefile: PlistBuddy before codesign.

2. **`-dirty` suffix in `CFBundleVersion`.** Apple accepts arbitrary
   strings here for DI builds, but if Comprador ever moves to App-
   Store distribution, `-dirty` would fail validation. For now it's
   a clear signal in dev builds.

3. **Release-cut friction.** Bumping `RELEASE_VERSION` in the
   Makefile is one more thing to remember at tag time. Consider
   sourcing from `git describe --tags --match 'v*' --abbrev=0`
   instead — automatically picks up the latest tag. Tradeoff: tag
   first, then build; vs the current "build then tag" flow.

4. **Existing apps installed before this change** report the old
   `0.1.0 (1)`. Once the architect reinstalls a build with the new
   plist, the .diag attribution becomes correct. No migration
   needed.
