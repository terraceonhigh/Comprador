## Items

### 1. Retire the WebDAV mount path entirely

**Symptom.** NFS has been the default mount path since v0.3.0
(2026-05-09). The WebDAV stack remains in tree for legacy reasons
but is no longer exercised by normal use. Every line of WebDAV-
adjacent code is:

- Surface area for security review (one of the SECURITY.md
  invariants is about the bridge's loopback-only binding; WebDAV
  and NFS each have their own listener and each is a place that
  invariant can regress).
- Cognitive load on every reader who has to figure out which path
  is "the path."
- Bytes in the shipped bundle.

**Scope.** The retirement removes:

- `bridge/webdav/` (the entire package) — handler, finder-quirk
  logic, resume endpoint, lock/unlock fakes, deadprops quota
  reporting.
- `bridge/resume/` (likely — used only by the WebDAV resume path).
- `MountManager.mount` (the WebDAV branch) in
  `MenuBarApp/Sources/MountManager.swift`, plus its supporting
  helpers and the `MountError` cases that only WebDAV produces.
- `MenuBarApp/Sources/ResumeCompanion.swift` and its companion-
  port wiring throughout `AppDelegate.connect`/`teardown`.
- The writeseq-cap heuristics and the bridge's `/_comprador/resume`
  endpoint.
- The `useNFS = true` flag in `BridgeProcess.start` (becomes
  unconditional).
- The bridge's `--nfs` CLI flag (becomes unconditional; whole
  `--proto webdav` branch goes).
- Documentation references: README "Architecture" mentions of
  WebDAV (already cleaned in this session, but cross-check),
  ARCHITECTURE.md WebDAV branch.

The "## WebDAV / Finder" section of MISTAKES.md should be
preserved as historical receipts of webdavfs quirks. Already
tagged with a sign-of-life note in the audit pass.

**Cost.** Substantial. Probably ~1/3 of the bridge codebase by
line count. But the diff is almost entirely deletions; the surface
that remains (NFS path) is already exercised in production.

**Trade-off.** Once WebDAV is gone, the writeseq-cap workarounds
go with it — including the resumable-uploads work captured in
[RESUMABLE-UPLOADS.md](RESUMABLE-UPLOADS.md). That work was real
engineering effort. Its lessons remain; the code that embodied
them does not.

**Sequence.** Probably best done as a single big PR rather than
incremental — half-deleted dead code is harder to reason about
than either "all there" or "all gone."

### 2. Retire the privileged helper

**Symptom.** Per [SECURITY.md](SECURITY.md), the helper is the
single largest privilege-escalation surface in the Comprador
bundle. After the NFS pivot (v0.3.0), the helper is no longer
invoked on the mount path — its remaining job is the cosmetic
`.local` hostname rewrite in `/etc/hosts` so the Finder sidebar
reads `/Volumes/Pixel-6` instead of `/Volumes/Pixel-6.local`.

That one cosmetic feature is the entire justification for shipping
a LaunchDaemon, SMAppService.daemon registration, BTM state, root-
privileged Unix-socket RPC, separately-notarized binary, and a
Login Items approval prompt on first launch.

**Fix options.**

- **A. Drop the feature entirely.** Accept `<DeviceName>.local`
  as the sidebar label. `.local` is idiomatic on macOS — AirDrop,
  Bonjour-discovered SMB, screen sharing all show it. Zero
  cosmetic loss most users would notice.
- **B. Move the cosmetic to a one-shot prompt at install.**
  AppleScript `do shell script with administrator privileges` for
  a one-time `/etc/hosts` write at first run. No persistent
  daemon, but one root prompt per device whose hostname needs
  rewriting (or a deferred batch on first attach).
- **C. Keep the helper as a tiny single-purpose daemon.** Same
  attack surface as today, just with a much smaller justifiable-
  feature footprint.

**Recommendation: A.** The `.local` suffix is not a real problem;
the helper is. The pre-launch consolidation session of 2026-05-10
already documented the helper as a v0.4.0 cleanup target. Trading
a one-character cosmetic for a 600+-line privileged-binary
elimination is a clear win.

**Scope.** With (A) chosen, the retirement removes:

- `helper/` (entire directory: Go source, plist, BUILD comments).
- `MenuBarApp/Sources/HelperClient.swift`.
- `BUNDLE_HELPER` Makefile recipe.
- The helper bundling step in `app-swiftc` and `app-signed`.
- AppDelegate's `installHelper` / `installHelperFlow` /
  `registerCleanHostname` / `teardownCurrentSession` (the helper
  bits).
- The "Helper installed / needs approval / install…" menu items.
- The SMAppService.daemon registration and notarization
  requirements for the helper.
- WelcomeWindow's helper-related copy (if any).

**Cost.** Smaller than #1 by line count (~600 lines vs ~3000) but
emotionally weightier — kills a feature that took real work to
ship. Worth the loss; the engineering lesson is preserved in
[MISTAKES.md "SMAppService / Helper"](MISTAKES.md).

**Sequence.** Can ship independently of #1, in either order.
Probably do #1 first because the helper's *only* user-visible
feature is the `.local` rewrite, and that decision is
self-contained.

### 3. Drop `com.apple.developer.system-extension.install` entitlement

**Symptom.** v0.3.0 shipped with this entitlement set; it requires
an embedded provisioning profile, which the CI workflow doesn't
provision; v0.3.1 hotfixed by switching CI to
`Comprador.debug.entitlements` (which omits it) — see
[CHANGELOG.md "v0.3.1"](../CHANGELOG.md). The production
entitlements file still carries it for the planned DriverKit
extension that has been on the roadmap since the seizure-race
debugging arc.

The ImageCaptureCore investigation closed without changing this —
[DECISIONS.md "ImageCaptureCore investigation"](DECISIONS.md)
explicitly preserves the dext on the roadmap. So the entitlement
is dormant, not dead.

**Fix options.**

- **A. Drop it entirely.** If we're not shipping the dext in
  v0.4.0 (or ever), the entitlement is just a future-self
  reminder; carrying it costs CI complexity.
- **B. Keep it but document.** Re-add the production-entitlements
  comment chain saying "this is for the future dext; the build
  signs against the debug entitlements until the profile is
  wired up."
- **C. Actually ship the dext.** Substantial work
  ([DEXT-DESIGN.md](DEXT-DESIGN.md)) — its own multi-week scope.

**Recommendation: B for v0.4.0, revisit at v0.5.0.** Don't drop
it (we'll regret it when the dext finally happens), but document
it so the v0.3.1 hotfix doesn't repeat.

**Cost.** Documentation only, ~10 minutes.

### 4. (Carryover) `.local` suffix decision

If item #2 chooses option (A) — drop the helper, accept `.local` —
then V0.3.3.md item #2 ("Strip the `.local` suffix from the Finder
sidebar label") closes with option C (accept and document). If
v0.4.0 chooses option B (one-shot install prompt), then V0.3.3 #2
closes with that.

Resolve here so V0.3.3 #2 can be marked closed.

### 5. Re-take the cgo callback buffer-reuse acceptance test

Carryover from
[DECISIONS.md "Vanquishing the per-callback VM_ALLOCATE leak"](DECISIONS.md):
the 9 GiB Attenborough vmmap retake is the spec'd acceptance
criterion for the cgo fix (physical footprint < 1 GB, VM_ALLOCATE
regions < ~50 vs the pre-fix 409). Today's partial confirmation
on a 49.6 MB transfer was directional but not spec-meeting. Worth
a single afternoon to actually run, capture, and close the
verification thread in DECISIONS.md.

## Out of v0.4.0 scope

Mirroring V0.3.3.md's hygiene:

- **True concurrent multi-device** (N phones, N Finder sidebar
  entries simultaneously). Scaffolding shipped in v0.3.3 (the
  DeviceSession class + sessions dict). The actual behavior
  unlock — relaxing the single-device guard in
  `handleDeviceAttached` and adding per-device menu UX — is
  PLAN-MULTI-DEVICE.md steps 5+6, separate scope.
- **Auto-update / Sparkle.** Mentioned in README's FAQ as
  on-the-roadmap; not gating anything; defer to v0.5.0.
- **iPhone support.** Not a goal (different protocol; documented
  in README's FAQ).
- **WebDAV-quirk lessons** — see the sign-of-life note added to
  MISTAKES.md "## WebDAV / Finder" section. The entries below
  that note become postmortems-on-removed-code once item #1
  here ships. They are preserved deliberately for the
  generalisable webdavfs lessons.

## Order of attack

If picking up incrementally, suggested order:

1. **#3 (entitlement docs)** — 10 min, lowest risk, removes
   future-Mercer confusion.
2. **#2 (helper retirement)** — biggest security win; if
   option A is chosen, the scope is concrete and bounded.
3. **#1 (WebDAV retirement)** — biggest line-count change;
   needs focused review pass. Best done as one PR.
4. **#4 (V0.3.3 #2 closure)** — resolves automatically once
   #2 is done; doc-only.
5. **#5 (cgo retest)** — independent; can slot in any time.
